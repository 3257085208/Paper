## 9.1 CPU：微周期配额——一次自查更正（图 22）

**背景。** 早期批次（qp2c：5 台满载客户 @50% 配额，周期 2/4/10/100 ms/1 s）曾显示“细周期把客户速率从 59% 提到 80%（+35%）”，并写入速览表。

**自查与更正（qp2v1）。** 投稿前按评审要求做计量核查：qp2c 的速率读数来自 burner 的**工作相位内累计平均**（每 ~2 s 覆写），而各配置仅隔 ~30 s——**后测配置的读数被前序快配置的窗口污染**（无配额段 25.6M 抬高早期读数）。干净复测：每配置**重启 burner**（全新累计窗口）+ 60 s 同步窗口 + 以 guest `cpu.stat` 交付量做地面真值：


**表 25。** 微周期自查：各配置交付 CPU、节流时间与速率

| 配置 | 交付 CPU | 节流占比 | 速率 | 速率/核 |
|---|---|---|---|---|
| 无配额 | 1.000 核 | 0% | 25.8M | 25.8M |
| 2 ms（50% 配额） | 0.500 核 | 50% | 13.2–13.4M | 26.4–26.8M |
| 1 s（50% 配额） | 0.500 核 | ~50% | 13.3M | 26.6M |

**更正结论。** 50% 配额下 **2 ms 与 1 s 交付完全相同**（各 0.500 核、≈52% 基线，差值 <1%）；**原“+35%”为测量伪影，已撤回**（速览表⑤同步更正）。服务侧不受周期影响（0.73–0.75 ms；qp2c 服务数据有效）。**教训（已固化进 `tb_qp2v.py`）**：吞吐对比必须（i）每配置重置累计窗口、（ii）以 cgroup 交付量而非速率文件做交叉验证。

**边界。** 纯 CPU 满载忙循环；延迟敏感/混合负载的周期效应未测（未来工作）。

## 9.2 内存：无 balloon 回收三件套（图 23–25）— 部分完成

**已完成（本批数据）。** （i）**KSM 舰队去重（ksm1；机制见内核文档[21]）**：64 台同镜像舰队共享 **21.4 GiB = 舰队内存的 33.4%**；ksmd 平均 ~0.16 核；服务 P99 0.73→0.76 ms（零回归）。代价边界：写入 CoW 长尾未测；跨租户去重存在已知侧信道议题，生产上按信任域分层启用。（ii）**空闲页上报（FPR）机制验证**：手动 300 MB——宿主 `memory.current` 315→629 MB 随分配、释放后 **6–12 s 回落**至原位，guest `MemTotal` 恒 973 MB 不变；附带发现：**空闲「1 GB」VM 的宿主实占仅 156–315 MB**（FPR 一直在归还空闲页）。（iii）**自动化 FPR（fpr5，300 MB）**：宿主 `memory.current` 571→875→570 MB（vm312）、581→878→575 MB（vm313），**回收 303 MB**，guest `MemTotal` 恒 973 MB——自动口径与手动验证一致（fpr4 曾因 balloc 调用缺 `debian@` 前缀未生效，修复后重跑）。（iv）**zram 吸收（zram3b，单位修复后）**：分配至 **1120 GB 达标**，其中 **176.8 GB 溢出全部进入 zram**（压缩后仅 3.1 GB 物理内存、`mem_used` 3.5 GB；compressible 冷页口径，真实负载压缩比会更低）；mid-storm 服务 P99 **0.745 ms 全程平**；对照**磁盘 swap 臂在 1044 GB 处中止**（96 GB swapfile 先耗尽）——“zram ✓ 吸收 / disk ✗ 不足”成立。（v）**QoE 金丝雀（canary3）**：两台独立金丝雀 VM 的 200 ms 唤醒循环在 baseline / rand40 / sync32 / mix50_40 四配置下 max gap 均 **0.1 ms**（>250 ms 停顿 = 0）——密度与相位编排下无调度停顿。

**指标口径**：宿主回收量（ksm sharing / memory.current 回落）、租户可见内存不变性（guest MemTotal/可用内存）、压缩/去重比、PSI 与探针延迟代价。

**已完成（ioc2，修复部署后）。** 8 台风暴客户 × 4K 随机 70/30 O_DIRECT × 60 s/臂：宿主 **~98k IOPS**、租户聚合 **~66k IOPS**（n=8）、租户侧单操作 P99max **8.3 ms**；三臂（none / static / adaptive）下服务 HTTP P99 **0.743–0.756 ms**——**租户 4K 随机风暴不触及服务**（隔离包络），三臂差异 <1%（本负载下自适应未显优势，如实报告）。

## 9.4 与“无回归”约束的关系

逐机制三笔账（密度增益 / 隐形代价 / 租户可见回归）：**KSM、FPR、隔离为零可见回归**（客户速率分布与可见配置不变）；**zram 的代价是宿主侧压缩开销**（服务侧零伤；压缩比按可压缩冷页口径如实标注）；**配额与 IO 上限的代价明码记在被限客户身上**（速率、排队）——与第 5 章“经济版 = 明码标价的回归预算”闭环。数据出处：ksm1（去重 21.4 GiB = 33.4%，ksmd ≈ 0.16 核，服务 P99 0.73→0.76 ms；代价边界：写入 CoW 长尾未测、跨租户侧信道议题按信任域分层启用）；fpr1/fpr5（空闲"1 GB"VM 宿主实占 156–315 MB；300 MB 分配回收 303 MB、guest 可见内存不变）；zram3b（三臂：none ~940 GB 无 swap 中止 / zram 1120 GB 达标、176.8 GB 溢出被吸收、P99 平 / disk 96 GB swapfile 先耗尽中止）。
